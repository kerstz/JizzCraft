# Playback benchmark

Command: `jizzcraft --bench <file> --seconds 30 --bench-gst-play`
Files: generated by `cargo xtask fixtures` (x264enc ultrafast, I420, 8 Mbit/s, AAC).
Machine: CachyOS, Wayland, AMD GPU (radv), `vah264dec` (VA-API) auto-selected.
Date: 2026-10-13. Release build. Window 30 s after 1.5 s warm-up.

CPU is a percentage of one core, process-wide (decoder threads included).

The baseline runs the external `gst-play-1.0` on a canonical `file://` URI. It
is a separate program, so JizzCraft's network guard does not apply to it: only
benchmark files you created yourself (`cargo xtask fixtures`).

## Reading the numbers honestly

- Playback is smooth and correctly paced on all three clips: no dropped frames,
  frame interval p95 within 0.2 ms of the nominal frame time.
- JizzCraft uses **3–6× more CPU than `gst-play-1.0`** on the same file. The
  reason is the MVP pipeline: decoded frames are downloaded from the VA-API
  surface, converted to RGBA on the CPU (`videoconvert n-threads=0`) and
  uploaded to a wgpu texture, where `gst-play` hands the surface to the
  compositor. The planned fix is NV12/I420 upload with YUV→RGB in a wgpu shader
  (see `ROADMAP.md`). Until then 4K30 costs more than one core.
- "Dropped" = GStreamer QoS drops + frames overwritten in the one-slot mailbox
  before the UI uploaded them. "Expected" is `fps × wall seconds`.
- Only H.264 was benchmarked here. Other codecs and hardware were not tested.
